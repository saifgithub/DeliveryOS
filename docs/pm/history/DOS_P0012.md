## 2. MABP v4 §16 — autonomous acceptance gates (`401ade0`)

A process-design conversation that turned into a doc rewrite. **Diagnosis:** the base MABP's three nested anti-fabrication defenses (Cycle 2 evidence manifest, Cycle 5 adversarial QA, Step-7 architect spot-check) can fail *together* because they are the same mechanism three times — an LLM reading fabricable text and asked to be skeptical. The manifest is just text; `npm test → passing` costs the same to fabricate as to earn. Two roots: verification-by-judgment-over-fabricable-evidence (the deeper one), and the architect's conflict of interest (orchestrate vs. audit = self-approval). A live demonstration landed mid-session: a verification sub-agent searched the wrong repos and confidently declared real, documented incidents "fabricated, zero evidence" — the exact failure being gated against.

**Fix (new §16, paste-ready, doc v3 → v4, v3 archived):** done-criteria become *executable* checks, authored by an **independent verifier (QA), not the implementer**, run by a **non-agentic gate** whose exit code is the verdict; **verifier triangulation** (≥2 blind authors) with **auto-advance on convergent green**; human dependency minimized to authoring intent, adjudicating divergences, and a sample audit. Amendments threaded through §3/§4/§6/§8/§9/§10/§14 (auto-advance replaces per-chunk approval; QA blind-authors before reading the builder report; spot-checks derive from the spec, as sampling; two new failure modes added).

Source of the idea: §16 of aegis-quant-classic's MABP (run-01 / CR015 / CR018 incidents). Ours inverts its emphasis — the buried "mechanical backstop" becomes load-bearing; the prose gates become a reference checklist.

## 3. Self-build gate (A) — and a latent bug it caught

Made §16's central claim real for DeliveryOS's own build: `scripts/gate.mjs` (clean → build → typecheck → test → package, exit 0/1, writes `docs/build/gate/last-run.json`), root `npm run gate`, and `.github/workflows/gate.yml` (PR + push to `main`, blocks merge on red). **On its first run it went red and surfaced a real pre-existing bug:** `npm run clean` removed `*/dist` but not the `contracts` composite `tsconfig.tsbuildinfo`, so a true from-clean build left stale incremental state — `tsc` exited 0 while emitting no `dist`, and the webview then failed to resolve `@deliveryos/contracts`. Everyday dev never hit it (buildinfo persists); a clean build does. Fixed `clean` to invalidate the buildinfo (literal path — rimraf 5 doesn't glob without `--glob`). Gate now GREEN: clean 149ms · build 3.0s · typecheck 1.2s · test 4.2s · package 0.8s.

Scope, stated plainly: this gates **DeliveryOS's own build only**. It is not generic.

## 4. Generic acceptance checks (B) — designed, not built

`docs/design/generic-acceptance-checks.md`. Decisive finding from exploring the product: **DeliveryOS today has the exact gap §16 names** — when a harness writes `result.md`, it is observed and parsed (`ResultWatcher`, `captureFromHandoff`), never *checked against the criteria*; verification criteria are prose (`{id, text}`) the harness is told to honour; CHUNK-14 is a human ticking checkboxes. The design closes it by reusing existing machinery (Test Designer specialist pattern, harness-profile registry + token substitution, `TerminalLauncher` exit-code capture, memory/links, the bypass surface): executable checks authored at brief-time (blind to the implementation by construction), canonical in DeliveryOS memory (not workspace-editable by the harness), run by a non-agentic profile-driven runner whose exit code feeds CHUNK-14. Sequenced into 5 gated chunks.
