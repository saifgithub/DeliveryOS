### Three-tier autonomous build orchestration — PILOT (CHUNK-12)

**Design.** The user proposed finishing the project with a single P-track session: me (Sonnet, PM) as orchestrator, spawning Sonnet implementer subagents per chunk, with Opus reserved as advisor for objective-failure escalation only. Key design decisions:

- Orchestrator does NOT invoke `/sm-start-fresh R` inside subagents (plan-mode approval loop stalls autonomous execution). Instead the orchestrator composes a self-contained implementation brief from the chunk spec and hands it directly to the implementer.
- Advisor escalation is **orchestrator-triggered from objective failure** (test count regression, typecheck error, unexpected files), NOT implementer self-reported. Avoids the well-known "I'll just power through" failure mode.
- Model tiering: Sonnet for orchestrator + implementer (cost-effective); Opus for advisor (expensive, used only on verifiable failure); Haiku reserved for CHUNK-16 (docs/retrospective).

**Pilot execution — CHUNK-12 (Result Capture).**

Commit: `25a78ae`. Tests: 292 → 312 (+20). Typecheck: ✅ both workspaces. Build: ✅ clean.

**Orchestrator verification.** All objective criteria passed on first attempt. No Advisor escalation needed.

**Key learning — orchestrator context problem.** Reading 10+ source files to compose a precise brief consumed ~70% of the orchestrator's context window. With 4 chunks remaining (CHUNK-13..16), the orchestrator would overflow before completing the chain.

**Resolution.** The orchestrator should read ONLY the chunk spec + BUILD_STATUS.md. The implementer (fresh context window) reads the codebase itself. The orchestrator's value is pre-resolving design decisions from the spec (e.g. "use cast-through pattern", "use execFile not exec"), not replicating codebase knowledge. This leaner approach is the carry-over for DOS:P3.
