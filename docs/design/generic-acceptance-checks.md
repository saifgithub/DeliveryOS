# Design — Generic per-delivery executable acceptance checks (MABP §16 in the product)

> Status: **design** (the "B" deliverable). Companion to the self-build gate (`scripts/gate.mjs`, the "A" deliverable) and to §16 of `docs/MULTI_AGENT_BUILD_PROCESS.md`. This is a real feature and should land as its own chunk/CR sequence, not in one pass.

## 1. Problem (grounded in the current code)

DeliveryOS orchestrates a delivery: discover → PRD → requirements → **test spec** (CHUNK-08) → **brief** (CHUNK-09) → **handoff** to a harness (CHUNK-11, Claude Code / Codex) → **result capture** (CHUNK-12) → **verification** (CHUNK-14).

Two findings from the code make the gap precise:

- **Criteria are prose.** `VerificationCriterion` is `{ id, text }` (`contracts/src/testDesigner.ts`). The brief tells the harness "you MUST satisfy every verification criterion" (`extension/src/brief/handoffSiblings.ts`), but that's an instruction, not an enforcement.
- **Results are observed, never checked.** `ResultWatcher` (`extension/src/handoff/resultWatcher.ts`) fires on `result.md`; `captureFromHandoff` (`extension/src/result/captureFlow.ts`) parses its six sections and stores them. **Nothing runs the criteria against the produced output.** Verification (CHUNK-14, `extension/src/panels/verification/`) is a human marking `failedCriteria` checkboxes in `VerificationApp.tsx`.

So the product reproduces the exact fabricable-evidence failure §16 is about: the pass condition is authored-by-and-trusted-from the implementer (the harness), and "done" means a file appeared. This design makes §16's contract real **inside the product**, for any delivery on any stack.

## 2. Goal

Per delivery, produce **executable acceptance checks** that are:

1. **Executable** — each criterion → a command/assertion that exits 0/1, bound to a named delivery surface (not prose).
2. **Independently authored** — generated by a DeliveryOS step (a "Check Author"), *before* handoff, **blind to the harness's implementation**; the harness can neither author nor edit them.
3. **Run non-agentically** — a runner executes them against the produced workspace and emits a machine verdict (exit code + per-check results); that verdict, not a human checkbox, is the gate.
4. **Generic** — works across target stacks via a runner-profile abstraction, the same way harness profiles already abstract Claude Code vs Codex.

This also advances "minimize human dependency": CHUNK-14 flips from *human marks every criterion* to *machine verdict first, human only on divergence/bypass*.

## 3. Design (reuse first — most pieces exist)

### 3.1 Data model (`contracts/src`)

Extend the criterion, don't replace it — preserve the existing prose `text` for humans and add an executable form:

```ts
// contracts/src/testDesigner.ts (extend) or a new contracts/src/acceptanceChecks.ts
export type CheckRunner = 'node-test' | 'pytest' | 'jest' | 'shell' | 'generic';

export interface ExecutableCheck {
  readonly id: string;              // EC-REQ-002-01
  readonly criterionId: string;     // -> VerificationCriterion.id (the prose it makes executable)
  readonly surface: DeliverySurface;// which surface it exercises (see §3.4)
  readonly runner: CheckRunner;
  readonly command: string;         // exit 0 = pass; bound to the surface
  readonly expect: string;          // human-readable expected observable (for the report)
  readonly authoredBy: string;      // verifier identity (NOT the harness)
}
```

Persistence: a new memory type `acceptance-checks` (mirror the `test-spec` pattern in `contracts/src/memory.ts` + `MEMORY_TYPES`), linked to the requirement via a new link kind `has-acceptance-checks` (`contracts/src/links.ts`). The **canonical checks live in DeliveryOS memory, not the workspace** — see §3.5 (independence).

### 3.2 Authoring — a "Check Author" specialist (independent of the harness)

Mirror the Test Designer specialist (`extension/src/specialists/testDesigner/`): `promptBuilder.ts` + `resultParser.ts`, new commands `checks/generate` / `checks/commit` on the messenger (alongside `testDesigner/commit`).

- Authors from the **requirement + test-spec** (the prose criteria), at **brief time — before handoff**. This ordering gives blind authoring (§16.3 G1) for free: the implementation does not exist yet.
- Each prose `VerificationCriterion` → one `ExecutableCheck` bound to a surface (G2/G3).
- **Triangulation (§16.4):** optionally fire ≥2 Check Authors with diversified lens/tier; converged checks proceed, divergence is surfaced. (Reuses nothing new — just spawn N and diff.)

### 3.3 Runner — non-agentic, profile-driven (the generic core)

Add a `CheckRunnerProfile` registry mirroring `extension/src/profiles/registry.ts` (`HarnessProfile` already has `command_template` + `${BRIEF_PATH}`/`${RESULT_PATH}` token substitution):

```ts
export interface CheckRunnerProfile {
  readonly name: CheckRunner;
  readonly command_template: string;   // e.g. 'node --test ${CHECK_FILE}'  (exit code IS the verdict)
  readonly output_format: 'exit-code' | 'tap' | 'junit' | 'json';
}
```

Reuse `extension/src/handoff/terminalLauncher.ts` (or a headless `child_process` variant) to run each check and capture the exit code via the existing `onClose` exit-code path. Output: a machine result `{ checkId, passed, exitCode, output }[]` + overall verdict, written to `.deliveryos-handoff/check-results.md` and persisted as memory. **The exit code is the verdict — no agent narrates it.**

Fires after `handoff/resultObserved`, before the human opens `VerificationApp`.

### 3.4 Delivery surfaces (per delivery, per stack)

This is the genuinely hard, generic part. The §16.5 surface table is stack-specific; for an arbitrary target the Check Author must map criteria to the target's surfaces (HTTP endpoint, CLI, persisted artifact, UI, etc.) and emit checks in the target's runner. MVP: support `node-test` + `shell` (covers DeliveryOS-like targets) and treat surface as a free-form tag; generalize the surface taxonomy later. **Do not pretend full generality on day one — `log()` the stacks not yet supported.**

### 3.5 Independence guarantee (the load-bearing constraint)

The harness runs in the workspace and could edit anything written there. To keep "the implementer cannot edit the checks":

- Canonical `ExecutableCheck` definitions are stored in **DeliveryOS memory**, written *before* handoff.
- The handoff includes the checks only as **read-only context** ("these exact checks will be run against your output") — the same way the test spec is handed over today.
- The runner executes the **memory-canonical** checks, regenerated to disk at run time, **ignoring any workspace copy**. Integrity: hash the canonical set at author time; if a workspace copy diverges, that's a flagged divergence, not an override.

### 3.6 Verdict integration (CHUNK-14, reduce human dependency)

Feed the runner's machine verdict into verification as objective evidence:

- **All checks green → auto-advance:** record a `pass` verification with the check evidence attached; no human checkbox required.
- **Any check red → divergence:** route to rework (or require an explicit, logged `bypass` — the mechanism already exists: `VerificationBypass` in `contracts/src/verification.ts`).
- Human is pulled in only on red checks, bypass, or a sampled audit — matching §16.4.

## 4. What to reuse (no reinvention)

| Need | Existing asset |
| --- | --- |
| Specialist (prompt + parse + commit) | `extension/src/specialists/testDesigner/*` |
| Profile registry + token substitution | `extension/src/profiles/registry.ts`, `types.ts` |
| Run a command, capture exit code | `extension/src/handoff/terminalLauncher.ts` (`onClose`) |

| Memory entry + links | `contracts/src/memory.ts`, `links.ts` |

| Handoff files | `contracts/src/handoff.ts` (`HANDOFF_PATHS`) |

## 5. Suggested sequencing (each its own gated chunk/CR)

1. **Data + contracts** — `ExecutableCheck`, `acceptance-checks` memory type, `has-acceptance-checks` link, `check-results` handoff path.
2. **Check Author specialist** — generate/commit executable checks at brief time (blind by construction).
3. **Runner + profile** — `node-test` + `shell` MVP; exit-code verdict; `check-results.md` + memory.
4. **Verification integration** — machine-verdict-first CHUNK-14; auto-advance on green, bypass/rework on red.
5. **Triangulation + generalization** — ≥2 authors; broaden surface taxonomy + runner profiles.

Each chunk is itself verified by the §16 process (its acceptance checks authored by an independent verifier, run by the gate) — the feature is built the way it preaches.

## 6. Open questions / risks

- **Surface generality.** Full per-stack surface mapping is open-ended; MVP must scope honestly and surface what it can't yet check, or a red-less "green" recreates the original lie one level up.
- **Check authority vs intent.** Same irreducible residual as §16: an independently-authored check can still encode a wrong reading of the spec. Triangulation narrows it; the human sample audit is the floor.
- **Runner sandboxing.** Executing generated commands against a workspace is the same trust surface as the harness terminal today; reuse the existing untrusted-workspace posture (`capabilities.untrustedWorkspaces` is already `supported: false`).
